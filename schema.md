# Schema

## Overview

The application uses Supabase Postgres tables in the `public` schema. The current code depends on three main tables:

- `prices`
- `messages`
- `users`

The exact table creation SQL is not present in this repository, so this document describes the schema inferred from the application code and the RLS policy script.

## Entity Relationship Summary

```text
Supabase Auth User
        |
        | matched by email
        v
public.users

public.prices       public.messages
public-facing       customer contact submissions
admin-managed       admin-readable
```

There are no explicit foreign keys used by the current JavaScript. Admin identity is matched by email between Supabase Auth and `public.users`.

## Table: public.prices

Purpose:

- Stores laundry and ironing price-list items.
- Public users can read this table.
- Admin users can create and delete records.

Fields used by the app:

| Column | Type | Required | Used By | Notes |
| --- | --- | --- | --- | --- |
| `id` | integer or bigint | yes | public and admin scripts | Used for ordering and deletion. Should be primary key. |
| `cloth_type` | text | yes | `laundry.js`, `admin.js` | Displayed as the clothing item name. |
| `ironing_price` | numeric or integer | yes | `laundry.js`, `admin.js` | Displayed with `NGN`. |
| `washing_price` | numeric or integer | yes | `laundry.js`, `admin.js` | Displayed with `NGN`. |
| `gender` | text | yes | `laundry.js`, `admin.js` | Current UI expects `Male` or `Female`. |
| `created_at` | timestamptz | optional | not directly used | Recommended for audit/history. |

Recommended SQL:

```sql
create table if not exists public.prices (
  id bigint generated by default as identity primary key,
  cloth_type text not null,
  ironing_price numeric(12, 2) not null check (ironing_price >= 0),
  washing_price numeric(12, 2) not null check (washing_price >= 0),
  gender text not null check (gender in ('Male', 'Female')),
  created_at timestamptz not null default now()
);
```

Read query used by public page:

```sql
select *
from public.prices
order by id asc;
```

Insert shape used by admin page:

```json
{
  "cloth_type": "Shirt",
  "ironing_price": 500,
  "washing_price": 1000,
  "gender": "Male"
}
```

Delete patterns used by admin page:

```sql
delete from public.prices where id = :id;
delete from public.prices where gender = 'Male';
delete from public.prices where gender = 'Female';
```

## Table: public.messages

Purpose:

- Stores customer contact-form submissions.
- Public users can insert through the contact endpoint.
- Admin users can read and delete messages.

Fields used by the app:

| Column | Type | Required | Used By | Notes |
| --- | --- | --- | --- | --- |
| `id` | integer or bigint | yes | `admin.js` | Used for ordering and deletion. Should be primary key. |
| `name` | text | yes | contact API, `admin.js` | Normalized and limited to 80 characters before insert. |
| `email` | text | yes | contact API, `admin.js` | Lowercased and limited to 120 characters before insert. |
| `message` | text | yes | contact API, `admin.js` | Normalized and limited to 2000 characters before insert. |
| `created_at` | timestamptz | recommended | `admin.js` | Displayed with `toLocaleString()` when present. |

Recommended SQL:

```sql
create table if not exists public.messages (
  id bigint generated by default as identity primary key,
  name text not null check (char_length(name) between 1 and 80),
  email text not null check (char_length(email) between 3 and 120),
  message text not null check (char_length(message) between 1 and 2000),
  created_at timestamptz not null default now()
);
```

Insert shape used by contact endpoint:

```json
{
  "name": "Customer Name",
  "email": "customer@example.com",
  "message": "Hello, I need laundry service."
}
```

Admin read query:

```sql
select *
from public.messages
order by id desc;
```

Admin delete patterns:

```sql
delete from public.messages where id = :id;
delete from public.messages where id >= 0;
```

## Table: public.users

Purpose:

- Stores application-level user profiles and roles.
- Used to decide whether an authenticated Supabase Auth user is an admin.

Fields used by the app:

| Column | Type | Required | Used By | Notes |
| --- | --- | --- | --- | --- |
| `id` | uuid, integer, or bigint | yes | `login.js`, `admin.js` | Selected but not used for joins in current code. |
| `username` | text | optional | `login.js`, `admin.js` | Selected for profile context. |
| `email` | text | yes | `login.js`, `admin.js`, RLS function | Must match Supabase Auth email. |
| `role` | text | yes | `login.js`, `admin.js`, RLS function | Must be `admin` for dashboard access. |
| `created_at` | timestamptz | optional | not directly used | Recommended for audit/history. |

Recommended SQL:

```sql
create table if not exists public.users (
  id uuid primary key,
  username text,
  email text not null unique,
  role text not null default 'user' check (role in ('user', 'admin')),
  created_at timestamptz not null default now()
);
```

If the `id` is intended to match Supabase Auth users, use:

```sql
id uuid primary key references auth.users(id) on delete cascade
```

Role check query used by login:

```sql
select id, username, email, role
from public.users
where email = :email
limit 1;
```

Admin check function from `scripts/supabase-security.sql`:

```sql
create or replace function public.is_admin()
returns boolean
language sql
stable
security definer
set search_path = public
as $$
  select exists (
    select 1
    from public.users
    where lower(email) = lower(auth.email())
      and role = 'admin'
  );
$$;
```

## Row-Level Security

RLS is enabled by `scripts/supabase-security.sql`:

```sql
alter table public.prices enable row level security;
alter table public.messages enable row level security;
alter table public.users enable row level security;
```

### prices Policies

Public read:

```sql
create policy "prices public read"
on public.prices
for select
to anon, authenticated
using (true);
```

Admin insert:

```sql
create policy "prices admin insert"
on public.prices
for insert
to authenticated
with check (public.is_admin());
```

Admin update:

```sql
create policy "prices admin update"
on public.prices
for update
to authenticated
using (public.is_admin())
with check (public.is_admin());
```

Admin delete:

```sql
create policy "prices admin delete"
on public.prices
for delete
to authenticated
using (public.is_admin());
```

### messages Policies

Anonymous insert:

```sql
create policy "messages anon insert"
on public.messages
for insert
to anon, authenticated
with check (true);
```

Admin read:

```sql
create policy "messages admin read"
on public.messages
for select
to authenticated
using (public.is_admin());
```

Admin delete:

```sql
create policy "messages admin delete"
on public.messages
for delete
to authenticated
using (public.is_admin());
```

### users Policies

Own profile or admin read:

```sql
create policy "users own profile read"
on public.users
for select
to authenticated
using (lower(email) = lower(auth.email()) or public.is_admin());
```

## Index Recommendations

Recommended indexes:

```sql
create index if not exists prices_gender_idx on public.prices (gender);
create index if not exists prices_id_idx on public.prices (id);
create index if not exists messages_created_at_idx on public.messages (created_at desc);
create index if not exists users_email_lower_idx on public.users (lower(email));
```

## Schema Change Rules

- Keep database column names in snake_case.
- Update JavaScript normalization when column names change.
- Keep RLS policies in sync with new tables and admin actions.
- Add constraints for values the UI already assumes, especially `gender` and `role`.
- Never depend only on client-side checks for protected operations.
